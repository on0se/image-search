# 設計判断

画像をクエリにして、似た画像を検索するアプリケーションの設計判断を記録する。

## 前提

```
要件      クエリ画像に視覚的に似た画像を探す
非要件    テキストによる検索
対象      スマホの写真
規模      1万枚程度を想定
利用形態  個人利用。デプロイしない
```

### 利用形態の判断

当初はデプロイして公開する想定で開発を始めた。

しかし写真は個人情報そのものであり、他人の写真を預かるには取り扱いの責任と法的な知識が必要になる。個人開発でそのリスクを負う判断はしなかったため、各自の環境で動かす形に切り替えた。

ただし個人利用であっても、実際に使う人がいることを前提に設計している。検索速度や待ち時間に関する判断は、自分だけが使うものとしてではなく、使う人の体験を基準に選んでいる。

この前提が、以下の技術選定すべての土台になっている。

---

## 1. 埋め込みモデルに DINOv2 を選定

### 比較

| | DINOv2 | CLIP | ResNet |
|---|---|---|---|
| ベクトル化の対象 | 画像 | 画像・テキスト | 画像（分類タスク想定） |
| 被写体が端にある場合 | 認識できる | 中央の特徴が支配的 | — |
| 類似検索での精度 | 最も高い | 高い | 中 |
| 出力次元 | 768 | 512 | 512〜2048 |

### 不採用の理由

| | 理由 |
|---|---|
| CLIP | テキスト検索が要件外なのでクロスモーダル性は不要。画像内の文字に反応しやすく、視覚的に無関係な写真が上位に来ることがある。精度もDINOv2にやや劣る |
| ResNet | 分類タスク向けのモデルで、類似検索には向かない |
| 自前学習 | 学習コストが高い |

### 採用理由

- 画像による類似検索で最も精度が高い
- 被写体が中心になくても認識できる

### 限界

| 弱点 | 今回の影響 |
|---|---|
| 768次元 | 後述の探索アルゴリズム・インフラ構成に影響する |

---

## 2. 前処理でパディングを選択

### 課題

DINOv2 は 224×224 の正方形入力を要求するが、スマホ写真の縦横比はバラバラ。

### 比較

| | 挙動 | 問題 |
|---|---|---|
| 直接リサイズ | 正方形に引き伸ばす | 被写体そのものが歪む |
| 中心切り出し | 中央を正方形に切る | 被写体が中心にない場合、対象そのものが消える |
| パディング | 黒で埋めて正方形にする | 黒帯が類似度に影響する |

### 判断

DINOv2 は被写体が画像の端にあっても認識できる。そのため、切り出しの「検索したい対象そのものが消える」というリスクを取る理由がないので、情報を落とさないパディングを選んだ。

**モデル選定がこの判断を可能にしている。** 中央付近の特徴が支配的なモデルを使っていた場合、切り出しの方が適切だった可能性がある。

### 限界

黒帯が特徴量に影響し、極端に細長い画像では内容より縦横比が類似度を支配しうる。ただしスマホ写真は最大でも 9:16 程度で、黒帯は面積の 44% が上限のため、この用途では許容範囲と判断した。

なお、黒帯が実際にどの程度影響するかは未検証であり、今後確認したい点として認識している。

---

## 3. 探索アルゴリズムを HNSW に変更

### 課題

当初は `IndexFlatL2`（総当たり）を使用していた。DINOv2 の出力が 768 次元と高いため、1件あたりの距離計算が重く、総当たりの処理時間が問題になった。

### 比較

| | IndexFlatL2 | HNSW |
|---|---|---|
| 探索方式 | 総当たり | グラフ探索 |
| 1件あたりのコスト | 768次元の距離計算 × 全件 | 探索経路上のノードのみ |
| 計算量 | O(N) | O(log N) |
| 探索結果 | 厳密 | 近似（精度低下は極小） |
| 差分追加 | できる | できる |

### 判断

近似最近傍探索の HNSW に切り替えた。差分更新に対応しており、計算コストが低く、かつ精度が高いため。

変更は 1 行で済む。

```python
index = faiss.IndexFlatL2(dim)
index = faiss.IndexHNSWFlat(dim, 32)
```

### トレードオフ

厳密解を捨てて速度を取った。精度は高いに越したことはないが、総当たりでは検索に時間がかかり利用者を待たせる。HNSW は精度の低下がごくわずかである一方で探索コストが大きく下がるため、体験を優先して近似を許容する判断をした。

### 限界

| 弱点 | 今回の影響 |
|---|---|
| グラフ構造の分だけメモリを使う | 1万枚規模では問題にならない |
| 削除が苦手 | 今回は削除機能がない |

---

## 4. ベクトルDBを導入しない

### 前提となる数字

```
1万枚 × 768次元 × 4byte = 約30MB
アクセスは単一プロセスからのみ
```

### 比較

| | FAISS（メモリ） | ベクトルDB |
|---|---|---|
| 形態 | ライブラリ | 別プロセス（サーバー） |
| 運用コスト | なし | 起動・管理が必要、障害点が増える |
| 永続化 | 自前 | 標準機能 |
| 適する規模 | 〜数百万 | 数千万〜 |

### 判断

30MB はメモリに載るため、検索は同一プロセス内で完結する。外部プロセスを挟む理由がない。

ベクトルDBは数千万件規模や、複数サービスから共有される場面で効く道具であり、この利用形態では運用コストが効果に見合わない。

### 移行が必要になる条件

| 条件 | 理由 |
|---|---|
| 複数人が同時に使う | プロセスをまたいでインデックスを共有する必要がある |
| 数百万件規模になる | メモリに載らなくなる |
| ベクトル化を別プロセスに分離する | プロセス間でメモリを共有できない |

---

## 判断の連鎖

これら 4 つは独立した選定ではなく、最初のモデル選定が後続を規定している。

```
DINOv2 を選定
    │
    ├─ 被写体が端でも認識できる
    │      └─ 中心切り出しが不要になり、パディングを選べた
    │
    └─ 768次元
           ├─ 総当たりのコストが膨らむ  → HNSW へ
           └─ 1万枚で30MB、メモリに載る → ベクトルDB不要
```

## 今後の展望

| 項目 | 課題と対応 |
|---|---|
| 大量アップロードの非同期化 | ベクトル化は1枚あたりの処理が重く、1万枚規模では同期処理で成立しない。キューとワーカーによる非同期化が必要になる |
| 複数ユーザーでの利用 | 対応するにはプロセス間でインデックスを共有する構成が必要になる |
